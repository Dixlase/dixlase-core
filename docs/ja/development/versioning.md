# 版の付け方

Dixlase がリリースにどう番号を付けるか、版の各部分が何を意味するか、そして拡張機能が
あるコアの上で動くかどうかをどの項目が決めるかを説明します。

このページは方針です。リリースを実際に切る手順は
[コアのリリース](releasing.md)にあります。

## 短く言うと

リリースはセマンティックバージョニング（`MAJOR.MINOR.PATCH`）に従います。

| 上げる桁 | 入るもの | 例 |
| --- | --- | --- |
| **PATCH**（`0.1.19` → `0.1.20`） | 不具合とセキュリティの修正。既定の挙動は変えません。マイグレーションは修正に必要な範囲だけです | セキュリティ修正、翻訳キーの訂正、終了時にキューを空にするようにした修正 |
| **MINOR**（`0.1.20` → `0.2.0`） | 新機能、既定の挙動の変更、新しい設定、Plugin API の変更 | メディアのファイルにタグを付ける機能、ファイルで管理するコンテンツの既定を「管理画面から公開」にする変更 |
| **MAJOR**（`0.x` → `1.0.0`） | Dixlase を本番運用に推奨できるようになった時点 | GA |

**PATCH と MINOR を分ける試験は「更新を当てる運営者が、何かを知っておく必要があるか」
です。** 何も読まずに当てられるなら PATCH です。リリースノートを読んで何かを判断する
必要があるなら（新しい設定、変わった既定、切っておきたい機能）MINOR です。

## 1.0 より下でも、新機能は MINOR である理由

セマンティックバージョニングは、後方互換のある機能追加の場所を MINOR と定めていて、
Dixlase はその規則に従います。メジャー版 0 は仕様の中で明示的に自由とされているため
（「いつ何が変わってもよい」）、0.x であることが MINOR の枠を特定の用途に使うよう
義務づけるわけではありません。

一部の生態系では、`0.y.z` の MINOR を破壊的変更の軸として扱う慣習があります。Composer
や Cargo のキャレットがそう書かれているからです（`^0.1.0` は `>=0.1.0 <0.2.0` の意味）。
この慣習が役に立つのは、**パッケージ管理経由で使われるライブラリ**で、版の範囲だけが
互換性を伝える手段である場合です。

Dixlase はアプリケーションで、しかも互換性を伝える明示的な手段を別に持っています
（後述の `requires.dixlase_api`）。ですから版番号は、運営者が本来それを読む目的
——「この更新はどれくらい大きいのか」——に使えます。MINOR は「新しいものがあります、
ノートを読んでください」という意味です。「拡張機能が動かなくなります」という意味では
ありません。

## 拡張機能の互換性を決めるのは `dixlase_api` で、コアの版ではありません

拡張機能の manifest（`plugin.json` / `theme.json`）は 2 つの異なるものを宣言していて、
役割も別です。

```json
"requires": {
    "dixlase": ">=0.1.0",
    "dixlase_api": "^0.1",
    "php": ">=8.3"
}
```

- **`dixlase_api` が互換性の契約です。** その拡張機能がどの Plugin API の版に対して
  書かれたかを示し、コアが拡張機能を読み込むときに確かめるのはこちらです。コア側は
  `App\Extension\ExtensionApi::CURRENT_VERSION` で、照合は
  `ExtensionCompatibilityChecker::check()` にあります。
- **`dixlase` は下限です。その拡張機能が動く最も古いコアを示します。** 上限ではなく、
  互換性の関門でもありません。`>=X.Y.Z` の形で書き、キャレットは使いません。

**`dixlase` は下限で書いてください。** キャレット（`^0.1.0`）は拡張機能をコアの
MINOR 1 つに黙って釘付けにするので、その拡張機能が使っていないものしか変わっていない
コアの機能リリースでも、インストールが拒まれます。それは意図ではなく、キャレットは
誰も見直さなかった初期値にすぎませんでした。

2 つの版は独立に動きます。コアが `0.1.x` から `0.2.0` に上がっても `dixlase_api` は
動かないので、`^0.1` を宣言している拡張機能には影響しません。

### それぞれがどこで効くか

2 つの判定で届く範囲が違うので、ここは正確に書いておきます。

| 判定 | 項目 | 走る場所 | 何をするか |
| --- | --- | --- | --- |
| 読み込み時 | `dixlase_api` | `PluginServiceProvider`、`ThemeServiceProvider` | ベータ期間中は警告を記録して読み込みを**続けます** |
| インストール / 更新 | `dixlase` と `php` | `dls:plugin:install`、`dls:plugin:update`、`dls:theme:install`、`dls:theme:update`（`EnforcesExtensionRequirements` 経由） | 操作を**拒みます** |
| 健全性スコア | `dixlase`、`php`、`dixlase_api` | `PluginHealthScorer` | 指摘として報告します。強制はしません |

はっきり書いておくべき帰結が 2 つあります。

- 管理画面のインストールと更新のボタンは同じ Artisan コマンドを呼ぶので、
  **インストール経路の拒否は管理画面にも効きます。** CLI だけの話ではありません。
- ファイルとして置かれた拡張機能（`git clone`、`rsync`、イメージのビルド、復元した
  バックアップ）はインストールのコマンドを通らないので、**`requires.dixlase` は
  まったく確かめられません。** 読み込み時の判定はもう一方の項目を読み、ベータ期間中は
  警告だけです。`dixlase-core#756` を参照してください。

## ベータ期間（`0.x`）

`0.x` の間、Plugin API は **公開済みですが、凍結していません。** `PLUGIN-API.md` に
列挙した要素は、設計が固まるまで互換性のない変更が入ることがあります。

- Plugin API の破壊的変更は MINOR リリースに乗り、PATCH には乗りません。そのとき
  `ExtensionApi::CURRENT_VERSION` を上げます。
- 破壊的変更はすべて `CHANGELOG.md` の **「Plugin API — Breaking」** の見出しに移行
  方法とともに記載します。可能な場合は旧シンボルを 1 リリース分残し、`@deprecated` を
  付けます。
- MINOR リリースに破壊的変更が入っている**必要はありません。** ほとんどは入りません。

Plugin API の凍結は `CHANGELOG.md` で告知し、`plugin-api-v1.0` タグで示します。
**特定のコアの版（1.0 を含む）とは結び付けません。** 凍結後の破壊的変更は MAJOR
リリースでのみ行い、少なくとも MINOR 1 サイクル分の非推奨期間を設けます。

## `1.0.0` は本番運用に推奨できることを意味します

`1.0.0` は、Dixlase を本番運用に推奨できるようになったときに付けます。特定の機能が
入ったという話ではなく、備えができたという表明です。`1.0` 以降、破壊的変更は MAJOR
リリースにしか乗りません。

## `main`、`next`、そして `-dev` の接尾辞

どのリポジトリにも長命のブランチが 2 本あり、版番号はどちらを見ているかを示します。

- **`main` は最新のリリースそのものです。** リリース済みの版（`0.1.20`）を名乗り、
  リリースを切るときだけ動きます。
- **`next` は開発中の次の版です。** その版に `-dev` を付けたもの（`0.1.21-dev`）を
  名乗り、既定のブランチです。

接尾辞があるのは、開発中のツリーがリリース**そのもの**を名乗らないようにするためです。
`next` を追うインストールが `0.1.20` を読むと、すでに 0.1.20 を持っていると信じて
しまいますが、実際に持っているのは 0.1.20 と未リリースのコミットです。
`version_compare` は `0.1.21-dev` を 0.1.20 より上・0.1.21 より下に置くので、追って
いるインストールが、すでに通り過ぎたリリースを勧められることはありません。

リリースの直後、`next` は次の PATCH に `-dev` を付けた版に上げます。そのリリースが
結果として MINOR になった場合は、リリースを切るときに直します。接尾辞は仮置きで、
次にどの桁が動くかの約束ではありません。

## 公開した番号は打ち直しません

いったん公開した版の番号は、使い切りです。間違いは次の版として出し、同じ番号を
打ち直すことはしません。

そうしないと、`0.1.20` と名乗る異なるツリーを 2 人の利用者が持つことになります。
しかもアップデータは、すでに入っている版への更新を勧めないので、訂正はすでに当てた
人に永久に届きません。

打ち直しが許されたのは、最初の公開リリースの前の 1 回だけです。

## ベータ期間に保守ブランチは置きません

長命の `0.1.x` ブランチはありません。リリース済みの版に対する急ぎの修正は、
**ホットフィックス**の経路を使います。`origin/main` から `hotfix/<issue>-<slug>` を
切り、そこからリリースし、`main` を新しいタグへ早送りして、`origin/main` を `next` に
マージします。

これで、保守ブランチがあれば扱えたはずの場面——`next` がすでに `0.2.0-dev` にある
のに `0.1.21` を出す——が、3 本目の長命ブランチなしに扱えます。「`main` は最新の
リリースそのもの」という決まりも壊れません。保守の系統を持つ価値があるかどうかは、
最新のリリースを追うだけでは済まない利用者が現れる GA の時点で、改めて判断します。

セキュリティの修正は、用意ができた時点で PATCH として出します。機能リリースを
待つことはありません。

## 拡張機能の版はコアと独立です

プラグインとテーマは、それぞれ自分の版と自分の履歴を持ちます。拡張機能の版がコアの版
と一致していても、それは同じ日にリリースされたという偶然で、関係があるわけでは
ありません。

PATCH / MINOR / MAJOR の意味は拡張機能にも同じように当てはまり、その拡張機能自身の
機能に対して読みます。

## リリースの仕組み

- **コア**は版を 2 つのファイルに持ち、両者は常に一致していなければなりません。
  `VERSION` と `dixlase.json` の `version` です。
  `php scripts/bump-version.php <x.y.z>` で両方を同時に上げます。食い違うと CI が
  失敗します。
- **拡張機能**は版を manifest（`plugin.json` / `theme.json`）と `composer.json`
  （プラグインは最上位の `version`、テーマは `extra.dixlase.version`）に持ちます。
  同じ名前の `scripts/bump-version.php` が両方を揃え、`package.json` がある場合は
  それも揃えます。
- 署名済みの拡張機能は、**版上げのあとに再署名します。** 署名が manifest と変更履歴を
  覆っているからです。署名はコミットとタグの直前、最後の工程です。
