# 更新とロールバックでのマイグレーションとシーダー

運用者がプラグインやテーマを更新したとき、またその更新をロールバックしたときに、コアが拡張機能のマイグレーションと `UpdateSeeder` をどう扱うか。そして、それが拡張機能の作者に何を求めるか。

英語版は [`docs/development/plugins/updates-and-rollback.md`](../../../development/plugins/updates-and-rollback.md)。

## 更新

`dls:plugin:update` / `dls:theme:update`(これを実行する管理画面のアップデート管理も同じ):

1. インストール済みのツリーをバックアップする。その時点のマイグレーションの最大の batch(`max_batch`)を添え書きに記録する。
2. 新しいリリースのファイルに差し替えてスキャンする。「ブロック」の版はここで元に戻し、以下は実行しない。
3. 新しいマイグレーションを実行する。リリースが足すマイグレーションは、すべて**1 つの新しい batch** に入る。
4. 拡張機能に `Database\Seeders\UpdateSeeder` があれば実行する。

## ロールバック

`dls:plugin:rollback` / `dls:theme:rollback`(拡張機能の画面のロールバックのボタンも同じ):

1. 更新で入ったマイグレーションを戻す。バックアップの `max_batch` より上の batch にある台帳の行を、それぞれの `down()` で戻す。
2. バックアップからファイルを戻す。

**`UpdateSeeder` が書いたものは戻さない。** 更新のマイグレーションが作ったテーブルに足した行は、そのテーブルと一緒に消える。もともとあったテーブルに書いた行は残り、前の版の拡張機能はその行がある状態で動く。

## 拡張機能の作者に求めること

- **マイグレーションには、ちゃんと動く `down()` を書く。** ロールバックが実行するのはこれ。
- **`UpdateSeeder` は追加だけにする。** `insertOrIgnore()` / `updateOrCreate()` で足し、既存の行を消したり書き換えたりしない。足すものは、前の版にとって害が無いようにする(その行があっても前のコードが動くこと)。
- **前の版が受け入れられない変更は、マイグレーションで行う。** そうすれば `down()` で戻せる。
- 更新前とまったく同じデータベースに戻す必要があるときは、更新前のデータベースのバックアップを復元する(`dls:backup:restore <id> --targets=database`)。ロールバックはそこまではしない。

## 経緯

コア v0.1.4 まで、ロールバックはバックアップ以降に増えた **batch の数**を `--step` に渡していたが、`--step` が数えるのはマイグレーションの**ファイル**。2 本以上のマイグレーションを含む更新は 1 つの batch に入るので、最後の 1 本しか戻らなかった([dixlase-core#455](https://github.com/Dixlase/dixlase-core/issues/455))。
