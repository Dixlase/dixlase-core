# Issue の書き方

Dixlase での GitHub Issue の使い方です。何を Issue にするか、どう書くか、どうラベルを付け、どう閉じるかを決めます。目的は、知られている問題のひとつひとつについて、報告から修正、リリースまでを公開の履歴でたどれるようにすることです。

英語版は [`docs/development/issues.md`](../../development/issues.md) にあります。

---

## Issue にするもの

**するもの**

- 不具合。メンテナー自身が見つけたものも含む
- 管理画面・インストーラ・ドキュメントの使い勝手の問題
- 機能の提案
- 脆弱性ではない守りの強化(多層防御、より安全な既定値)
- 公開で追う価値のある技術的な負債
- ドキュメントと翻訳の誤り

**しないもの**

- **修正前の脆弱性。** 非公開で報告してください([SECURITY.ja.md](../../../SECURITY.ja.md))。修正を出したあと、メンテナーが GitHub Security Advisory を公開します。公開の Issue を作る場合も、修正を出したことの記録だけにします。
- 特定の本番環境の詳細。ホスト名、パス、認証情報、個人情報を含むログなど。
- 非公開リポジトリの内部事情。

**どこに書くか**

- 問題があるリポジトリに書きます。プラグインの不具合は、そのプラグインのリポジトリです。
- 複数のリポジトリにまたがる問題は `dixlase-core` に 1 件立て、ほかのリポジトリからはそこへリンクします。

---

## 編集の前に Issue

コアと公式のプラグイン・テーマのソースを編集する前に、その変更の Issue を立てるか、すでにある Issue を探します。ブランチと Pull Request はその Issue を指します(説明に `Fixes #N` と書く)。

**例外。** 次の場合は Issue は要りません。

| 理由 | 対象 |
| --- | --- |
| `security` | 修正前の脆弱性。非公開で直し、修正を出したあとに Security Advisory で公開します([Issue にするもの](#issue-にするもの)を参照) |
| `release` | リリースのための版上げと CHANGELOG の記入 |
| `signing` | プラグイン・テーマの再署名 |
| `dependencies` | 依存関係の更新。Dependabot の Pull Request を含む |
| `generated` | 生成ファイルの作り直しだけで、手で編集していないもの |
| `typo` | 意味の変わらない誤字の修正 |

例外の Pull Request は、説明に 1 行でそう書きます。

```
No issue: release
```

**作業中に別の問題を見つけたとき。** 同じ変更の中では直さず、別の Issue を立てます。1 つの Pull Request は 1 つの Issue に答えます。

**チェック。** すべての Pull Request でワークフローが動き、説明が Issue を指していない(`#N`・`owner/repo#N`・Issue の URL のどれも無い)うえに上の理由も書かれていなければ失敗します。HTML コメントの中の文字は数えないので、テンプレートの例だけでは通りません。Dependabot の Pull Request は対象外です。

## タイトル

コミットメッセージと同じ英日併記にし、先頭に領域を付けます。

```
<領域>: <英語の要約> / <日本語の要約>
```

例:

```
core-update: the admin sees a 500 during the vendor swap / コア更新: vendor の入れ替えの間に管理者に 500 が出る
extensions: installing without a token hits the GitHub rate limit / 拡張機能: トークン無しのインストールで GitHub の利用制限に当たる
```

外部の報告者は、英語か日本語の片方だけでかまいません。もう片方は、仕分けのときにメンテナーが足します。

領域は `area:` ラベル(下記)と合わせます。

---

## 本文

バグ報告と機能の提案は、`.github/ISSUE_TEMPLATE/` の入力フォームを使います。

メンテナーが自分で見つけたものは、**既知の問題(Known issue)** のフォームで書きます。本文は、英語のまとまりと日本語のまとまりを `---` の行で区切って並べます。まず英語ですべての項目を書き、そのあと日本語ですべての項目を書きます。項目ごとに英日を交互に書かないでください。それぞれの言語が、ひと続きの文章として読めるようにするためです。

項目は次のとおりで、どちらの言語でも同じ順に並べます。

| 項目(英 / 日) | 内容 |
| --- | --- |
| What happens / 何が起きるか | 見えた現象を 1〜2 文で |
| Impact / 影響 | 誰が、どの版から、どの程度困るか |
| Reproduction / 再現手順 | 手順と、その手順を試した版 |
| Cause / 原因 | 分かっていれば。推測なら推測と書く |
| Proposed fix / 直し方の案 | あれば(任意) |
| Done when / 完了の条件 | 何が満たされたら閉じてよいか |

```markdown
### What happens
…
### Done when
…

---

### 何が起きるか
…
### 完了の条件
…
```

推測ではなく、見たことを書きます。サイトの状態(入れているプラグイン、プリセット、HTTPS かどうか)によって再現が変わる場合は、それも書きます。

## ラベル

すべての Issue に、**種類**のラベルを 1 つと、**領域**のラベルを 1 つ以上付けます。**優先度**と**状態**のラベルは、仕分けのときに付けます。

正本は [`.github/labels.yml`](../../../.github/labels.yml) です。

| 分類 | ラベル |
| --- | --- |
| 種類 | `bug`、`enhancement`、`docs`、`hardening`、`chore`、`question` |
| 領域 | `area:core-update`、`area:extensions`、`area:install`、`area:admin`、`area:front`、`area:security`、`area:i18n`、`area:api`、`area:ci` |
| 優先度 | `P0`(リリースを止める・データを失う)、`P1`(次のリリースで直す)、`P2`(都合のよいときに) |
| 状態 | `needs-repro`、`confirmed`、`blocked` |
| 閉じた理由 | `duplicate`、`wontfix`、`invalid` |

優先度は GA ロードマップの段階に合わせます。

---

## マイルストーン

直す予定のリリースを、マイルストーンとして付けます。例: `v0.1.4`、`v0.2.0`、`GA`。マイルストーンの無い Issue は、まだ予定に入っていないという意味です。

予定が変わったらマイルストーンを付け替えます。出し終えたリリースに Issue を残したままにしません。

---

## Issue からリリースまで

1. Issue を直す Pull Request の説明に `Fixes #N` と書きます。マージすると Issue が閉じ、squash のコミットに PR の番号(`(#M)`)が残ります。
2. CHANGELOG には PR の番号を書きます。議論が Issue にある場合は、Issue の番号も書きます。
3. Issue を閉じるとき、メンテナーが修正の入った版をコメントします。
   ```
   Fixed in v0.1.4 (#M). / v0.1.4 で修正しました(#M)。
   ```
4. 直さずに閉じる Issue には、閉じた理由のラベル(`wontfix`・`duplicate`・`invalid`)と、理由を 1 行書きます。

これで「報告 → Issue → PR → リリース」の流れを、どこからでもたどれます。

---

## 仕分け

- 外部からの報告には、数日のうちにメンテナーがラベルを付けて返事をします。
- 再現しない報告には `needs-repro` を付け、足りない情報を尋ねます。30 日たっても返事が無ければ、再開できる旨を添えて閉じます。
- Issue の中のコードは参考情報として扱います([CONTRIBUTING.ja.md](../../../CONTRIBUTING.ja.md))。修正はメンテナーが書き直します。

---

## 言語

Issue は英語でも日本語でも書けます。メンテナーはタイトルを英日併記にし、どちらの言語でも返事をします。
