# 監査ログ整合性（ハッシュチェーン）

## 概要

Dixlase の監査ログは、改ざんを**検知**するための仕組みを 2 つ重ねています。改ざんを防ぐものではなく、また何かを保証するものでもありません。

- **行ごとのハッシュチェーン（鍵付き）。** 各行は、13 項目と前の行のハッシュに対する HMAC-SHA256（`record_hash`）を持ち、鍵はサイトの整合性の鍵（`INTEGRITY_KEY`）です。行を書き換えても、鍵が無ければハッシュを計算し直せません。鍵を設定する前に書かれた行はただの SHA-256 のままで、そのまま検証を通ります（「整合性の鍵」を参照）。
- **日ごとの日次封印（鍵付き）。** 完了した 1 日ごとに、件数・最初と最後の行・最後の行のハッシュに対する HMAC-SHA256 を記録します。鍵は同じく整合性の鍵です。鍵を設定する前に作られた封印は元の鍵（`AUDIT_LOG_SECRET`、未設定なら `APP_KEY`）のままです。

どちらも監査ログと同じデータベースに置かれます。行は、それを書き込むのと同じトランザクションでチェーンにつながれます（「行をつなぐ時点」を参照）。封印は毎日自動で作られ、検証は毎日スケジュールで行われます。すべての行を計算し直す全件検証は手動で実行します。この仕組みが証明できる範囲は「セキュリティ考慮事項」を参照してください。

## 行をつなぐ時点（設計上の判断）

#629 で決めた内容です。

**行は書き込み時にチェーンにつなぎます。** `AuditLog::log()` は 1 つのトランザクションの中で、
行を挿入し、その時点のチェーンの先頭の後ろにつなぎます。書き込みは 1 行だけのロック用テーブル
（`audit_log_chain_lock`）で直列化します。各書き込みはまずその行を更新するので、次の書き込みは
トランザクションが終わるまで待ちます。検証はチェーンを id の順にたどり、待っている書き込みはまだ
id を取っていないので、挿入もロックの中で行います。

- アップグレード前から残っている行や、つなぐのに失敗した行は、古い順に 1 回の書き込みにつき
  100 件まで先につなぎます。それより多く残っている場合は新しい行も待たせ、
  `audit:integrity build` がまとめて順につなぎます。
- つなぐのに失敗しても、行はチェーンに入らないまま書き込まれ、毎時の `audit:integrity build` が
  つなぎます。チェーンを整えるために監査の行を捨てることはしません。
- チェーンの先頭より小さい id のまま残っている行は、順序を崩さずにはつなげません。チェーンに
  入れないまま残し、`build` が残件として報告します。
- 代償は、監査対象の操作 1 回につき更新 1 回とロック付きの読み取り 2 回で、監査対象の操作は
  ロックの順番を待ちます。呼び出し側がすでにトランザクションの中にいる場合、ロックはその
  トランザクションが終わるまで保持されます。

ほかの案は、バッチの間隔を短くする（空白は残る）ことと、重大な行だけを書き込み時につなぐ
（揃っていなければならない経路が 2 つになる）ことでした。

**行ごとのハッシュには鍵を付け、ローテーションできるようにしました（#665）。** #629 では、
ローテーション無しに鍵を付けると最初に鍵を変えたときに改ざんに見えるため、鍵を付けずにいました。
いまは行と封印がそれぞれ署名した鍵の版を持ち、検証は設定されているすべての版を受け付けるので、
過去の行や封印を検証失敗にせずに鍵を入れ替えられます。

**この仕組みが主張すること。** チェーンと封印が検知するのは、**データベース上で**行われた変更です。
アプリケーションのプロセスの中で動くコードは、同じ経路で行を書け、同じ鍵も読めるので、
アプリケーション全体が乗っ取られた場合は対象外です。

## 整合性の鍵

チェーンと封印の鍵は、`.env` の 1 つの秘密から作ります。

```dotenv
INTEGRITY_KEY=3:base64:...            # 現在の鍵: 新しい行と封印に署名する
INTEGRITY_PREVIOUS_KEYS=2:base64:...  # 以前の鍵（カンマ区切り）: 検証だけに使う
```

各項目は `<版>:base64:<鍵>` の形で、版は 2 以上、鍵は 32 バイト以上です。チェーン・封印・
鍵の開始記録（後述）は、この秘密から HKDF で用途ごとに派生させた別々の鍵を使います。

同じ鍵で、コアがデータベースの外で信頼する 2 つのファイルも封印します。
[ファイル整合性のベースライン](../security/file-integrity-check.md#封印)と、データベースに届く前の
起動時に読む有効プラグインの一覧（`storage/framework/cache/enabled_plugins.json`）です。
一覧が検証を通らないときはキャッシュ無しとして扱い、その要求ではプラグインの providers を
登録せず、不一致をログに残し、データベースから作り直します。鍵を参照する拡張機能のコードは、
プラグインのスキャナーが報告します（`dangerous_api.integrity_key`）。

`.env` に置くのは、チェーンが守る対象であるデータベースの外で、バックアップのアーカイブにも
入らないためです。そのため、バックアップを別のサーバーに復元するときは鍵を手で移してください。
移さないと、復元した行と封印は `key_unavailable` で失敗します。

### 鍵を作る

新しいサイトでは、インストーラーが作ります。既存のサイトは、運用者が次を実行するまで
これまでどおり動きます。

```bash
php artisan dls:integrity:key          # .env に INTEGRITY_KEY=2:... を書き込む
php artisan dls:integrity:key --show   # 書き込まずに行を表示する（.env が読み取り専用のとき）
```

更新の処理が `.env` を書き換えることはありません。鍵ができるまでは、サイトヘルスが作成を
推奨し、チェーンは鍵なしのまま、封印は元の鍵のままです。

最初の鍵を作ると、既存のファイル整合性のベースラインも、作り直さずにそのまま封印します。

### 鍵をローテーションする

```bash
php artisan dls:integrity:key --rotate
```

次の版の新しい鍵を書き込み、古い鍵を `INTEGRITY_PREVIOUS_KEYS` に移します。以後に書かれる
行と封印は新しい鍵を使い、それより前のものは古い鍵で引き続き検証されます。古い鍵は、それで
署名したものを残しているあいだは消さないでください。消すと、それらの行と封印は
`key_unavailable` で失敗します。

鍵の作成とローテーションは監査ログに記録されます（`integrity_key_created`、
`integrity_key_rotated`）。どちらのあとも、次を行ってください。

- 設定をキャッシュしている場合は `php artisan config:cache` を実行する
- 常駐するプロセス（キューのワーカー、スケジューラー）を再起動して新しい鍵を読ませる。
  それまでは古い鍵で署名し続けますが、その署名も検証を通ります。

### 版

| 版 | 行 | 封印 |
|----|----|------|
| 0 | ただの SHA-256（鍵を付ける前に書かれた行） | — |
| 1 | — | `AUDIT_LOG_SECRET`、未設定なら `APP_KEY`（鍵を付ける前に作られたすべての封印） |
| 2 以上 | その版の鍵による HMAC-SHA256 | その版の鍵による HMAC-SHA256 |

版 1 の封印が検証を通るのは、`AUDIT_LOG_SECRET`（未設定なら `APP_KEY`）を変えないあいだだけです。

### 鍵付けが始まる地点

版 0 の行は鍵なしで検証を通るので、どこでも受け付けると、鍵付きの行を鍵なしの行に書き換えられて
しまいます。そこで、各版の鍵が最初にハッシュした行を `audit_log_key_epochs` に、その版の鍵で
署名して記録します。最も早い有効な開始記録から後では、次のようになります。

- 鍵なしの行は `unkeyed_after_keying` で失敗する
- 鍵付きの行は、その行以前に有効な開始記録が要り、無ければ `key_epoch_missing` で失敗する
- 署名が合わない開始記録があると、検証全体が失敗する

開始記録を消したうえで鍵付きの行をすべて鍵なしに書き換える改ざんは、チェーンだけでは
見つかりません。ただし鍵付きの日次封印が完了した日の最後の行を押さえているので、その書き換えが
できるのは、まだ封印されていない行に限られます。

## 仕組み

### ハッシュチェーン

```
[Log 1] ──hash──> [Log 2] ──hash──> [Log 3] ──hash──> ...
   │                 │                 │
   └─ genesis        └─ hash(Log 1)    └─ hash(Log 2)
```

各ログレコードには以下のフィールドが追加されます：

| フィールド | 説明 |
|-----------|------|
| `record_hash` | このレコードのSHA-256ハッシュ（64文字） |
| `previous_hash` | 前レコードのハッシュ（最初は'genesis'） |
| `chain_sequence` | チェーン内の連番 |
| `hash_algorithm` | 使用アルゴリズム（`hmac-sha256`、鍵なしの行は `sha256`） |
| `hash_key_version` | その行をハッシュした整合性の鍵の版（0 = 鍵なし） |
| `verification_status` | 検証結果（valid/invalid/null） |
| `last_verified_at` | 最終検証日時 |

### ハッシュ計算対象

```php
$data = implode('|', [
    $this->id,
    $this->occurred_at->toIso8601String(),
    $this->severity,
    $this->outcome,
    $this->category,
    $this->action,
    $this->actor_type,
    $this->actor_id,
    $this->target_type,
    $this->target_id,
    $this->ip_address,
    json_encode($this->context),
    $previousHash,  // 前レコードのハッシュ
]);

// 鍵付きの行（hash_key_version が 2 以上）
$hash = hash_hmac('sha256', $data, $chainKey);

// 鍵を付ける前に書かれた行（hash_key_version 0）
$hash = hash('sha256', $data);
```

鍵の版そのものは `$data` に入りません。版を変えても、ハッシュと合わない鍵が選ばれるだけです。

## 日次封印（Daily Seal）

完了した 1 日ごとに、その日のログを日次封印で押さえます。行の削除・挿入や、日の末尾の書き換えは、封印と合わなくなることで検知されます。

### 日次封印テーブル

| フィールド | 説明 |
|-----------|------|
| `seal_date` | 対象日 |
| `first_log_id` | その日の最初のログID |
| `last_log_id` | その日の最後のログID |
| `log_count` | ログ件数 |
| `final_hash` | 最終ログのハッシュ |
| `daily_signature` | 封印の HMAC-SHA256 |
| `key_version` | 封印の鍵の版（「版」を参照） |

## コマンド

### ハッシュチェーン構築

```bash
# 未処理のログにハッシュチェーンを設定
php artisan audit:integrity build

# 処理件数を制限
php artisan audit:integrity build --limit=500
```

### 整合性の検証

```bash
# 標準の検証: 全日次封印 + 前回の検証位置以降のチェーン
php artisan audit:integrity verify

# 全件検証: 全日次封印 + チェーン全行
php artisan audit:integrity verify --all

# ID範囲を指定して検証
php artisan audit:integrity verify --from=1000 --to=2000

# 特定日の日次封印を検証（その日のチェーンも含む）
php artisan audit:integrity verify --date=2025-12-20
```

標準の検証が対象にするもの:

- **全日次封印（1日あたり O(1)）。** 封印の HMAC を再計算し、件数と最終ハッシュを照合します。
  保持期間内の全日について、行の削除・挿入、末尾の書き換え、封印の行の改ざんを検知します。
- **前回の検証位置以降のチェーン（O(行数)）。** すでに `valid` と記録された行は再ハッシュせず、
  その最後の行を起点として以降を検証します。

対象に**ならない**もの: 検証済みの行を `record_hash` を変えずにその場で書き換えた場合。
これはその行を再ハッシュしないと検知できないため、`verify --all` を定めた頻度で実行してください
（週次が妥当な既定です）。増分検証のたびにコマンドがその旨を表示します。

日次封印または行の検証に失敗した場合、あるいは以前の検証で改ざん検知済みの行が残っている場合、
コマンドは 0 以外の終了コードを返します。

### 日次封印作成

```bash
# 過去7日分の日次封印を作成
php artisan audit:integrity seal

# 日数を指定
php artisan audit:integrity seal --days=30

# 特定日の日次封印を作成
php artisan audit:integrity seal --date=2025-12-20
```


## プログラムからの使用

### ハッシュチェーン付きでログを記録

```php
use App\Models\AuditLog;

// 通常のログ記録（ハッシュチェーンなし）
AuditLog::log([
    'category' => AuditLog::CATEGORY_AUTH,
    'action' => AuditLog::ACTION_LOGIN,
    'actor' => $member,
]);

// ハッシュチェーン付きでログを記録
AuditLog::logWithHashChain([
    'category' => AuditLog::CATEGORY_SECURITY,
    'action' => AuditLog::ACTION_SETTINGS_UPDATED,
    'actor' => $member,
    'context' => ['changes' => $changes],
]);
```

### 整合性検証サービス

```php
use App\Services\AuditLogIntegrityService;

$service = app(AuditLogIntegrityService::class);

// チェーン検証
$result = $service->verifyChain();
if (!$result['is_valid']) {
    // 改ざん検知
    foreach ($result['errors'] as $error) {
        Log::alert('Audit log tampered', $error);
    }
}

// 日次封印作成
$seal = $service->createDailySeal(now()->subDay());

// 日次封印検証
$result = $service->verifyDailySeal(now()->subDay());

// 統計取得
$stats = $service->getStats();
```

### 改ざん検知時の対応

```php
// 改ざんが検知されたログを取得
$tamperedLogs = AuditLog::tampered()->get();

foreach ($tamperedLogs as $log) {
    // アラート送信
    app(SystemNotificationService::class)->sendAdminNotification(
        'Audit Log Tampering Detected',
        "Log ID {$log->id} has been tampered with.",
        ['audit_log_id' => $log->id]
    );
}
```

## 管理画面

### サイトヘルス

ダッシュボードの **サイトヘルス**（詳細モード）に、`AuditLogIntegrityService::getHealth()`
に基づく **監査ログ整合性** の項目が表示されます:

| 状態 | バッジ | 意味 |
|------|--------|------|
| 改ざん検知 | 重大 | レコードまたは日次封印の検証に失敗している |
| チェーン停滞 | 警告 | 2 時間以上チェーンに連結されていない行がある — 書き込み時の連結に失敗し、毎時の `audit:integrity build` も動いていない |
| 封印の遅れ | 警告 | 直近の完了日（ログあり）の日次封印が翌日 04:30 を過ぎても無い — 日次の `audit:integrity seal` が動いていない |
| 鍵なし | 推奨 | 整合性の鍵が設定されておらず、チェーンが鍵なしになっている（ほかに悪い状態が無いときだけ表示）。`php artisan dls:integrity:key` を実行する |
| 検証が古い | 推奨 | 連結から 30 日以上経っても一度も検証されていないエントリがある、または最も古い検証が 30 日以上前（増分検証では古い行は更新されないため `verify --all` を実行する）。前回の検証以降に連結された行は未検証で正常なので対象外 |
| OK | OK | チェーンと日次封印が最新（初日は OK 表示: 日次封印は完了した日にしか存在しない） |

これは cron 未設定に対する安全装置です。これが無いと、スケジューラが動いていないままチェーンが
静かに空のままになります。この状態は 5 分間キャッシュされ、`audit:integrity` を実行するたびに
クリアされます。

### 監査ログ詳細

監査ログ詳細画面に、各エントリのチェーン連番・レコードハッシュ・検証状態
（検証済み / 改ざん検知 / 未検証 / 未連結）・最終検証日時を表示します。いずれも読み取り専用で、
上記のコマンドが更新します。

## 推奨運用

### 定期タスク（Scheduler）

チェーン構築・封印・検証はコアが `routes/console.php` でスケジュール登録済みです。Laravel の
スケジューラ（cron から `php artisan schedule:run`）を動かす以外の設定は不要です:

| タスク | スケジュール |
|--------|--------------|
| `audit:integrity build` | 毎時（書き込み時につなげなかった行をつなぐ） |
| `audit:integrity seal` | 毎日 03:30（03:00 のファイル整合性スキャンの後） |
| `audit:integrity verify` | 毎日 03:45（封印の後） |

行は書き込み時にチェーンにつながれます。Web インストーラの完了時にもチェーンを 1 回構築し、
ロック用テーブルができる前に書かれた行をつなぎます。

生成は常時有効で、ON/OFF はありません。レコードは後から遡って保護できないため、保護を
「誰かが実行を思い出すこと」に依存させないためです。検証は毎日実行します（差分の
`audit:integrity verify`。PCI DSS 10.4.1 が求める日次レビューに当たります。NIST AU-9 は頻度を
定めていません）。失敗すると、**セキュリティ → 整合性** を開ける管理者全員に、管理画面全体の
バナーが出ます。通知とメールサーバーを設定していれば、管理者向けの通知メールも送ります。
メールは失敗を最初に見つけたときに 1 回だけ送り、バナーは後の検証が通るまで残ります。
手動の `verify` や `verify --all` も同じようにバナーを出し、消します（範囲の一部だけを見る
`--date` や `--from`/`--to` の実行は除く）。定期実行は差分なので、`verify --all` も定期的に
実行してください（「整合性の検証」を参照）。

### セキュリティ考慮事項

1. **整合性の鍵の保護**: チェーンと封印が検知するのは**データベース上の**改ざんです。`.env` まで読める攻撃者は両方を計算し直せ、アプリケーションの中で動くコードも同じです。鍵の漏えいを疑ったらローテーションし（「鍵をローテーションする」を参照）、以前の鍵は、それで署名したものを残すあいだ残してください。鍵を付ける前の封印は `AUDIT_LOG_SECRET`（または `APP_KEY`）のままなので、それらを残すあいだは変更しないでください
2. **定期検証**: 定めた頻度で `audit:integrity verify` を実行し、定期的に `verify --all` も実行する（「整合性の検証」を参照）
3. **アラート設定**: 通知先のメールアドレスとメールサーバーを設定し、毎日の検証の失敗をバナーに加えてメールでも受け取る
4. **バックアップ**: 日次封印テーブルも含めてバックアップ
5. **アクセス制限**: 監査ログテーブルへの直接アクセスを制限

## 技術仕様

### ハッシュアルゴリズム

- **レコードハッシュ**: チェーンの鍵による HMAC-SHA256（鍵を付ける前の行は SHA-256）
- **日次封印**: HMAC-SHA256
- **鍵の派生**: `INTEGRITY_KEY` から HKDF-SHA256 で、用途ごとに 1 つ

### 検証エラーコード

| コード | 説明 |
|--------|------|
| `hash_mismatch` | レコードのハッシュが一致しない |
| `chain_broken` | 前レコードへのリンクが切れている |
| `sequence_gap` | シーケンス番号に欠番がある |
| `invalid_genesis` | 最初のレコードが不正 |
| `redaction_unrecorded` | 消去済みの印があるのに、それを説明する消去の記録が無い |
| `key_unavailable` | レコードの鍵の版が設定されていない（その鍵が `.env` から消された） |
| `unkeyed_after_keying` | 鍵付けが始まった地点より後に、鍵なしのレコードがある |
| `key_epoch_missing` | 鍵付きのレコードの前に、有効な鍵の開始記録が無い |

### 消去済みのレコード（個人データの消去）

メンバーの個人データを消去すると（プライバシー → 消去）、監査ログの行は残したまま
`ip_address` を空にし、ほかの識別情報を置き換えます。`ip_address` はレコードの
ハッシュの対象なので、消去した行は自分のハッシュと一致しなくなり、消した値が無い以上
ハッシュを計算し直すこともできません。

そこで消去は自身を記録します。運用者と本人（id のみ）を示す `privacy_data_erased`
の行を 1 行書き、匿名化した各行に `redacted_at` と `redaction_id`（その行の
`request_id` と同じ値）を付けます。消去の行を書けなかった場合は消去そのものを拒み、
何も変更しません。

検証は消去済みの行を次のように扱います。

- 行自身のハッシュは確かめません。チェーン上の位置は引き続き確かめます。次の行の
  `previous_hash` と日次封印がその `record_hash` を押さえているので、行を消したり
  並べ替えたりすれば気づきます。
- 消去の行が存在し、その行の `redaction_id` を持ち、その行のアクターを対象として示し、
  その行より後にあることが必要です。満たさない場合は `redaction_unrecorded` で失敗します。
- 受け入れた行は **消去済み**（検証ステータス `redacted`）として数え、正常とも改ざんとも
  しません。改ざんの警告も出しません。

ハッシュの対象外の項目（`user_agent` / `actor_name` / `target_label`）は、もともと
ハッシュで守られていません。上の「ハッシュ計算対象」を参照してください。

この仕組みより前に匿名化された行には `redacted_at` が無く、引き続き `hash_mismatch`
で失敗します。どの消去が変えたかを示す記録が無いため、遡って埋めません。

### パフォーマンス

- ハッシュ計算: 約0.1ms/レコード
- チェーン検証: 約1,000レコード/秒
- 日次封印作成: 約0.5秒/日
